## 1. PRODUCT
**Problem.** A family needing blood forwards a WhatsApp message to hundreds of irrelevant people. Eligible nearby donors are hard to identify, stale requests keep circulating, donors get repeat spam, rare groups are nearly impossible, donor numbers leak publicly.
**Solution.** A location-aware donor-matching platform for Pune, Maharashtra. A *verified* request → *compatible, eligible, nearby* donors → contacted in *controlled escalation tiers* → auto-closed.
**Thesis: "500 random forwards vs 5 intelligent matches."** Three benefits visible within 30 seconds and recurring in the UI: **SPEED, PRECISION, TRUST**.
**Honesty rule.** RaktSetu is a donor *discovery* aid, not a medical authority; compatibility, eligibility and crossmatching are confirmed by the treating hospital and qualified staff. All data is synthetic and every simulated thing is labelled as such.

## 3. ARCHITECTURE
- **Layers:** `types/` → `lib/` (pure domain, no React) → `store/` (thin Zustand slices) → `components/`, `app/` (UI only; no business rules in UI).
- **Pure core.** `lib/` functions take `(state, input, clock, rng)` and return new values. Time is an injected `Clock`; randomness is an injected seeded PRNG (mulberry32).
- **Event-sourced requests.** Lifecycle changes are typed `DomainEvent`s (`RequestCreated`, `VerificationSucceeded`, `VerificationFailed`, `TierNotified`, `DonorAccepted`, `DonorDeclined`, `UnitsFulfilled`, `RequestExpired`, `RequestCancelled`, `ContactRevealed`, `PiiPurged`) applied by a pure `reduce(state, event)`. State = fold of events. The audit log, demo scrubbing, previous-step, reset and recovery all fall out of this.
- **Real vs demo isolation.** Demo mode runs on a sandboxed copy of state with its own simulated clock, never writes to persistence, and exiting restores real state.
- **Simulated donor responses (live mode).** A toggle "Auto-simulate donor responses" (default ON, off in demo except scripted overrides). Each notified donor responds after a seeded delay with accept-probability = `responseRate`. Donors can also act manually via the Phone Mock. The simulation lives in `lib/simulation`, is pure, and is driven by the simulated clock.
- **Simulated clock.** One `Clock` for the app: default runs at 1× real time with a fast-forward control (1×/5×/20×/jump +10 min). Demo uses its own clock instance.
- **Config.** All constants in `lib/config.ts`, each with a comment. Eligibility intervals carry the exact comment `// Verify against NBTC/official guidelines.`

- **Colleges:** MIT Academy of Engineering, COEP Technological University, VIT Pune, PICT, PCCOE, MIT-WPU, plus other local institutions; about 40% of donors affiliated, correlated geographically.
- **Last donation:** about 25% inside the cooling-off window so eligibility filtering visibly matters. Include donors exactly at day N−1, N, N+1 of the interval for both sexes (for boundary tests).
- **Phones:** `maskedPhone` like `+91 XXXXX XX482`. `revealPhone` uses an obviously fictional pattern `+91 00000 NNNNN`. No real numbers, no real people.

## 6. MATCHING ENGINE (`lib/matching`, pure, exhaustively unit-tested)
**A. Compatibility (RBC).** Recipient ← donors: O- ← O-; O+ ← O-,O+; A- ← O-,A-; A+ ← O-,O+,A-,A+; B- ← O-,B-; B+ ← O-,O+,B-,B+; AB- ← O-,A-,B-,AB-; AB+ ← all. Derive donor→recipients by **inverting this table in code** (no second hand-typed table); test consistency. Exact matches are prioritized. Show the medical disclaimer in UI and README.
**B. Eligibility.** Eligible iff opted in AND availabilityStatus = 'available' AND whole days since last donation ≥ interval (men 90, women 120; configurable) AND compatible. N−1 days → ineligible; N days → eligible.
**C. Score** = `0.45·proximity + 0.25·exactMatch + 0.20·reliabilityScore + 0.10·responseRate`, each in [0,1]. `proximity = exp(−d/λ)`, `λ = 8 km` (config), `d` = Haversine km. `exactMatch ∈ {0,1}`. Sort: score desc → exact match first → distance asc → donor id asc (stable, deterministic). Return a per-component breakdown for the UI.
**D. Escalation (non-rare).** Tier 1: top 5 eligible donors within 5 km. Tier 2: after 10 simulated minutes with no acceptance, expand to 10 km, next 10 donors. Tier 3: after a further `TIER3_DELAY_MIN` (default 15), expand to 25 km, next 20 donors, and flag nearby blood banks. All radii, counts and intervals are in config. Tiers draw only from not-yet-notified donors; a donor is never notified twice per request. If a tier has fewer candidates than its quota, notify those available and record the shortfall. No further tiers fire once accepted units ≥ required units, or the request is closed.
**E. Rare groups (A-, B-, AB-, O-).** Skip tiers. In one operation notify all eligible compatible donors within 30 km, capped by `MAX_NOTIFICATIONS_RARE`. Prominent **RARE BLOOD GROUP** banner. If the pool is tiny, say so honestly.
**F. Limits and counters.** `MAX_NOTIFICATIONS_PER_REQUEST` (default 35). Expose: total compatible, total eligible, total notified, total accepted, remaining eligible, estimated WhatsApp reach.
**WhatsApp reach (illustrative model, labelled "simulated illustrative estimate, not a measurement").** `reach = groupsReached × avgGroupSize × (1 − overlapFactor)`, defaults ≈ 500, all in config. `notificationsAvoided = max(0, estimatedReach − actualNotified)`.

## 7. LIFECYCLE, VERIFICATION, EXPIRY, PRIVACY
**Lifecycle:** created → verification pending → verified → matching → tier notifications → accept/decline → escalate → fulfilled → expired/closed/cancelled → archive.
**Verification (simulated):** two factors, a hospital confirmation code and a requester OTP. Deterministically generated fictional codes shown in the UI as "DEMO CODE: …". **Unverified requests can never trigger notifications**: enforced by the type system, by the pure engine (returns an error result) and by a test. Show a PENDING VERIFICATION badge until success. Max 3 attempts, then the request is `rejected`.
**Expiry:** closes when units are fulfilled, `expiresAt` passes, or the requester cancels. Closed requests leave active matching, appear in the archive with a prominent **STALE** label, and can never notify again.
**Retention:** 24 simulated hours after closure, a `PiiPurged` event removes requester contact details; the anonymized request remains.
**Contact privacy:** donor phones are masked everywhere. Only after a donor accepts is the contact revealed to the verified requester of that request. Each reveal appends an `AuditEntry` (actor, requestId, donorId, timestamp; never PII). Reveal authorization is a pure function (denied if unverified, not accepted, request closed, or wrong request).
**Health data:** store only blood group and last donation date. Self-check answers (recent illness, tattoo/piercing, medication, travel) are held only in transient component state, never persisted, logged or audited. They are demo screening, not a medical decision.
**Privacy Center must state:** what is collected and why; who sees it; when contact is revealed; what is deleted and when; what is never collected; that verification and storage are local simulations, not production-grade identity or medical verification.

## 9. DEMO MODE (the key presentation feature)
A floating **RUN DEMO** button starts a deterministic ~3-minute scripted walkthrough. Implement as a **pure timeline**: `buildDemoTimeline(seed) → DemoEvent[]` with absolute simulated timestamps, plus a controller that applies events to the sandboxed state and its own clock. Scrub, previous-step, reset and recovery = "replay from start to time t". Scripted overrides force the key outcomes (a specific donor accepts at a fixed time) so the story never depends on luck. Never depends on any external service.

Scenes (named chapters, each with a target duration and a state assertion in tests):
1. **The Problem:** a fictional forward "URGENT! B+ blood required. Please forward." spreads across groups and keeps circulating.
2. **The Request:** critical B+ request, 2 units, Ruby Hall Clinic; show verification with the demo codes.
3. **Intelligent Matching:** map activates; compatible → eligible → nearby; score breakdowns; Tier 1 notifications; hospital pulse and arcs.
4. **Escalation:** fast-forward; Tier 1 waits; Tier 2 fires; radius ring expands; notification panel updates.
5. **Donor Acceptance:** phone mock receives the notification, completes the self-check, accepts; contact reveal; donor→hospital arc.
6. **Closure:** simulated donation events fulfil both units; request closes; the old forward is stamped **STALE**; side-by-side comparison.
7. **Intelligence:** auto-navigate to Heatmap, then Forecast; highlight underserved areas and recruitment opportunities.
8. **Final Impact:** donors identified, notified, accepted, units fulfilled, time to first acceptance, notifications avoided, all derived from scenario state.

Controls: pause, resume, next, previous, reset, speeds 1×/5×/20×, a progress timeline with clickable chapter markers, keyboard shortcuts (Space, ←/→, R). Any scene can be re-entered cleanly after a misclick. Exiting restores the user's real state. Test: running the whole timeline headlessly twice yields identical final state.

## 10. DESIGN: cinematic healthcare command center
Not a generic SaaS dashboard: emergency-response ops room × premium fintech × clinical intelligence.
- Tokens defined once (CSS variables / Tailwind theme): near-black charcoal base, blood-red primary, warm amber for urgency, cyan/teal for donor activity, muted white/grey text. No ad-hoc hex values in components.
- Restrained glassmorphism, hairline borders, layered translucent panels, sparing glows, subtle grain.
- Large editorial Space Grotesk headlines, DM Sans body, tabular mono numerals for counters/timers.
- Purposeful motion only (counters, ring expansion, arc flow, panel transitions). Honour `prefers-reduced-motion`.
- Avoid excess rounded cards, gratuitous gradients, decorative charts, empty hero sections, cluttered navigation.
- Targets: 1280×720 and 1440×900, plus a projector-friendly **Presenter mode** (larger type, higher contrast, simplified chrome). Mobile-friendly donor phone and request screens.
- Accessibility: WCAG AA contrast, visible focus rings, full keyboard navigation, ARIA labels on map controls, live regions for new requests and acceptances, colour is never the only signal.
- First 30 seconds: the landing map already shows motion and meaning (live columns, pulsing hospitals, a visible request feed, the "500 vs 5" thesis in the header or empty state).

## 11. RELIABILITY
Global error boundary plus boundaries around the map, deck overlay and each chart. Every async path has loading, empty and error states. API routes return typed error envelopes. If the JSON store is missing or corrupt: back it up, reseed, and notify the user (never crash). No unhandled promise rejections. Zero console errors on the main flows. WebGL-unavailable and tile-unavailable fallbacks exist.

## 12. FALLBACKS (use rather than loop)
- deck.gl + MapLibre trouble → non-interleaved overlay; last resort: SVG/canvas map (the demo must still work).
- Font package issue → system font stack with the same CSS variable names.
- Chart issue → simple SVG chart.
- Anything else → simplest honest implementation + Known Limitations entry.
